### 2.2.6.2 — Schedule Engine

| ID | Test | Result | Notes |
|---|---|---|---|
| B2.1 | Named schedule maps to correct cron | **PASS** | `POST /monitoring/jobs` with `{domain:"example.com", schedule:"weekly", scanType:"quick"}` → `nextRunAt: "2026-08-10T08:00:00.000Z"`. Test ran on Saturday 2026-08-08; 2026-08-10 is the following Monday at 08:00 UTC, matching the spec'd `weekly` → `0 8 * * 1` cron mapping (confirmed against `monitoring.schedule.ts`). |
| B2.2 | Scheduler picks up due jobs | **COULD NOT VERIFY — see note below** | Requires a job with `nextRunAt` already in the past, which nothing in the public API can produce (schedules are always computed forward from "now"; `PUT` only recomputes forward). This needs either direct database access to backdate `nextRunAt`, or waiting for a schedule to become naturally due. Additionally, the B2.4 result below (a completed scan whose run never got picked up by the reconcile pass even after 15+ minutes) is strong evidence that **the automatic monitoring schedule pass is not currently running on staging** — most likely `MONITORING_SCHEDULE_ENABLED` is unset/`false` there (this env var defaults to `false` in `backend/src/config/env.ts`). See "Steps to verify from the website / ops" below. |
| B2.3 | No duplicate enqueue | **PASS** | Triggered the same job twice back-to-back via `PATCH /monitoring/jobs/:id/trigger`. First call: `200`, run created (`status:"pending"`). Second call, immediately after: `409` with `{"error":"A run is already in progress (started ...)."}`. Note: this validates the guard through the manual-trigger endpoint — `dispatchMonitoringJob()`'s in-flight check (`monitoring.engine.ts`) is the exact same function used by both the manual trigger and the scheduled dispatch pass, so this is a direct test of the shared guard, even though the literal cron-triggered race isn't independently reachable from outside the server process. |
| B2.4 | Run resolves on scan completion | **FAIL** | Triggered a quick scan monitoring run at 08:48:23 UTC. Polled `GET /monitoring/jobs/:id/runs` every 15s for over 15 minutes — run stayed `status:"pending"` throughout, `updatedAt` never advancing past its creation timestamp. Cross-checked the underlying scan directly via `GET /auth/my-quick-scans/:id`: it had already reached a terminal state (`status:"failed"`, unrelated reason — `example.com` was skipped as a stub page) at 09:05:43 UTC. The MonitoringRun was still `pending` 10+ minutes after that. This means the reconcile pass (`runMonitoringReconcilePass` in `monitoring.engine.ts`), which is responsible for resolving `pending`/`running` runs once their underlying scan finishes, never ran during the test window on staging. |

**Section result: 2/4 PASS, 1 FAIL, 1 could not verify** — both open items point to the same likely root cause: the monitoring schedule/reconcile loop does not appear to be active on the staging environment.

**Recommended before re-test:** ask backend/ops to confirm `MONITORING_SCHEDULE_ENABLED=true` (and check `MONITORING_SCHEDULE_INTERVAL_MS`) is actually set in staging's backend environment/container, and confirm the process that calls `runMonitoringSchedulePass()` on an interval is running there. Once confirmed active, B2.2 and B2.4 should be re-run.

#### Steps to verify B2.2 / B2.4 from the website (only if backend config can't be changed/confirmed directly)

These two can't be meaningfully driven from the website UI alone — there's no button that fast-forwards a schedule — but here's the closest real-world equivalent, useful once the scheduler is confirmed running:

1. Log in at `https://staging.silversurfers.ai` with the Pro test account.
2. Go to the account menu → **Monitoring** → **+ New Monitor**.
3. Set up a monitor with a real, scannable domain (avoid placeholder domains like `example.com` — this test run's scan failed because the target page had almost no content) and the **Weekly** schedule.
4. Immediately note the **Next Run** time shown on the monitor card — it will be the upcoming Monday at 08:00 UTC.
5. Come back to the Monitoring page after that time has passed (no action needed in between — this is the actual B2.2 scenario, a job becoming due on its own schedule).
6. **Expected (B2.2):** a new run appears in the job's Run History automatically, and **Next Run** has advanced to the following occurrence, without anyone clicking "Run Now."
7. **Expected (B2.4):** within a few minutes of that run completing, its row in Run History shows a final **Score** and status (not stuck on "Processing") — confirming the reconcile pass resolved it.
8. If step 6 or 7 doesn't happen by a day or so after the scheduled time, that reproduces this session's finding and points at the same staging scheduler issue.
